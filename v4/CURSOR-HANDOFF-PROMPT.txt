You are the senior developer and analyst reviewing **MiniMax Game Studio Ultra V4**,
a 3D game development environment built as a web application (Three.js r169 +
Vite 7, no game framework).

Review the code in this repository. You are READ-ONLY: do not edit any file.

## The request

V4 is an integrated AI-assisted 3D game development environment: an editor and
a runtime that share one ECS world and one Three.js scene, plus a playable
vertical slice.

The acceptance criteria you must judge against:

1. The editor works: hierarchy panel, inspector, 3D viewport, selection,
   move/rotate/scale, grid snapping, orbit/pan/zoom, duplication, undo/redo,
   save/load, lighting and material controls, play/edit modes, collision
   visualisation, camera preview, scene validation. Editor changes must
   survive a save and a reload.
2. The runtime works: a character controller that is camera-relative, an
   animation state machine with idle/walk/run and jump/landing, an NPC
   behaviour system with states, patrol, detection, pursuit, pathfinding and
   avoidance, a physics world with static-collider resolution, an event bus,
   a HUD, save/load, and pause/resume.
3. The vertical slice is genuinely playable: start, load a 3D scene, control a
   character, move through the environment, see animation, interact with an
   object, watch NPC behaviour, read a live HUD, pause and resume, save and
   reload, see performance figures, exit without errors.
4. Every claim in `v4/docs/` is backed by a reproducible measurement.

## Where the code is

- `v4/src/core/` — ECS, transforms, events, serialisation, scene manager,
  project, clock, logger.
- `v4/src/render/` `v4/src/input/` `v4/src/physics/` `v4/src/anim/`
  `v4/src/audio/` — the runtime subsystems.
- `v4/src/editor/` — the editor.
- `v4/src/npc/` `v4/src/gameplay/` `v4/src/levels/` — NPC behaviour, the
  gameplay modules and the demo level.
- `v4/src/assets/` `v4/src/ai/` — the asset library and the AI tooling.
- `v4/src/main.js` — the integration point. Read this first: it is where the
  subsystems are wired together, and where most integration defects have
  historically lived.

## What to look for, in priority order

1. **Correctness.** Logic errors, state-machine mistakes, ordering bugs
   between the ECS, the physics world, the scene manager and the Three.js
   scene. Anything that would only appear under a slow frame, a resize, a
   mode switch or a save/load.
2. **The save/load contract.** The save format holds *data* only. Runtime
   handles (a mixer, a mesh, a callback) must never reach it. A load must
   restore both the data *and* the behaviour — check that every runtime handle
   rebuilt after a load is rebuilt in every path that a load can take.
3. **The input model.** One key press must trigger exactly one action. The
   fixed-step clock can run up to five catch-up steps in a single frame;
   edge-triggered input must be consumed by the first of them
   (`Input.consumeEdges()`), and no other path may re-read the edge.
4. **Resource and performance problems.** Per-frame allocation, unbounded
   growth, GPU resources that are never disposed, listeners that are never
   removed, and anything that would degrade a long session.
5. **Error handling.** A failing subsystem must never take the frame loop
   down. Check the paths where a subsystem is absent (the editor is loaded
   optionally; the level may fail to build).
6. **Presentation.** Is the editor usable? Does the HUD tell the truth? Is the
   code readable by the next engineer?
7. **Honesty.** Does every number in `v4/docs/` correspond to a measurement
   the documented command actually produces?

## Context you need

- **The save format stores the hierarchy as entity ids**, and never stores
  runtime handles. `toPlainData` is the safety net, not the design.
- **Entity ids are per world.** A scene load clears the world and recreates
  the entities with the same ids.
- **The editor owns the camera in edit mode**; the runtime rig owns it in play
  mode. The app must not fight the editor for it.
- **The editor emits `mode:changed`** and the app subscribes. Mode is never
  set behind the editor's back.
- **The level owns the NPC system**, because it is the only thing that knows
  which navigation cells its own buildings block. The app adopts it.
- **Dynamic imports must be literal.** A variable path is not statically
  analysable and 404s in the production build.
- **The app owns the canvas**; the editor adopts it into its viewport.
- In three.js r169, `Camera.getWorldDirection(target)` calls
  `target.set(...).normalize().negate()`, and `Object3D.lookAt()` with a plain
  `{x, y, z}` yields NaN.
- The inspector must show runtime handles read-only, and caps JSON-editable
  values at 4,000 characters.

## Known, deliberate limitations — do not report these as defects

1. Apple Silicon is untested (the machine is x86_64). The gate is open.
2. 69 2D images are quarantined because their licences are unverified.
3. No audio assets ship — the cleared catalogue has none.
4. Nine gameplay modules (combat, inventory, dialogue, checkpoints, menus,
   pause, settings, objectives, HUD) are starter modules, separately testable,
   but not all exercised by the demo level.
5. Windows, Linux and non-Chromium browsers are untested.
6. There is no native build.
7. The LLM adapter is disabled by default and always falls back to the
   deterministic path.

## What to return

A review, not a summary of the code. For each finding:

- **Severity** — major (breaks a stated acceptance criterion or corrupts
  state), minor (a real defect with a workaround), or note (an improvement).
- **Where** — `file:line`.
- **What is wrong** — the concrete failure, and the sequence of events that
  triggers it.
- **Why it matters** — what a user or the next engineer would observe.
- **The fix** — a specific change, not a direction.

If you find nothing in a category, say so explicitly rather than inventing
findings. If you believe a documented claim is wrong or unsupported, name the
document and the claim, and say what evidence would settle it.
